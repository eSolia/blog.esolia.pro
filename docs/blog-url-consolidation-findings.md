# Findings — blog URL consolidation and the quality review that followed

**Status:** living record · **Started:** 2026-09-19 · **Repos:**
`blog.esolia.pro`, `esolia-2025`

Companion to
[`blog-url-consolidation-plan.md`](./blog-url-consolidation-plan.md). The plan
says what we intended to do. This says what we actually found doing it,
including the things the plan got wrong. Appended to as work continues.

## The one thing worth remembering

**Seven separate bugs in this migration share a single shape:** something that
bakes in or consumes a URL, running where it cannot see the `/blog` prefix, in a
build whose output tree is never restructured.

`base_path` rewrites `href`, `src`, `srcset`, `imagesrcset` and `form action` in
`.html` and `.css` pages. That is the whole of its reach. It does **not**:

- move files in `_site/`, so `outputPath` stays unprefixed
- touch anything running at `afterBuild`, or any plugin registered after it
- touch static file copies
- touch the contents of a `<script>` block, including JSON-LD
- touch anything generated by Worker code
- help a value that is already root-relative when some other code resolves it

Every one of the seven failed **silently** — a warning at most, never a build
error. Several looked fine in the HTML and only broke at runtime.

| # | What broke                                           | Where                                                                                    | Found by                 |
| - | ---------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------ |
| 1 | Every web font 404s                                  | `afterBuild` sed scripts ran after `base_path`                                           | grep of built CSS        |
| 2 | Site search dead                                     | Pagefind `type="module"` selector matched a now-prefixed `src`                           | grep of built HTML       |
| 3 | PWA icons 404, `start_url` leaves the blog           | static `manifest.json` copy                                                              | reading the build output |
| 4 | Double opt-in and unsubscribe 404                    | Worker-rendered confirm page's `<form action>`                                           | reading Worker source    |
| 5 | Every listing image broken                           | `picture`/`transform_images` matched a prefixed `src` against an unprefixed `outputPath` | user report              |
| 6 | `/blog/en` → the **main site's** homepage            | forwarder passed the blog's root-relative `Location` through                             | user report              |
| 7 | Structured data advertised a 301 URL and a 404 image | `json_ld` resolved a root-relative value against the origin                              | audit                    |

**Working rule for anything else touched here:** ask _"does this bake in or
consume a URL?"_ first. If yes, check it against the deployed site, not the
build log.

## Part 1 — the migration itself

### Plan gaps, blog side

The plan's two open questions both resolved to "no further work":

- **`base_path` does rewrite `<form action>`** — `action: "form[action]"` is in
  lume's `core/utils/dom_links.ts` selector table. No hardcoding needed.
- **`lume -s` does override `location`** — `getOptionsFromCli` reassigns it
  unconditionally in serve mode. CMS preview was never at risk, and the
  speculative `LUME_LOCATION` env var was not built.

Beyond those, the blog side needed six things the plan had not listed: the four
regressions above (items 1–4), `externalLinksIcon`'s hardcoded origin, and the
blog's own stale absolute self-references.

### Plan gaps, esolia-2025 side

One was a **blocker**: `src/lib/content/redirects.ts` mapped `/blog` and
`/blog/` to `blog.esolia.pro`. Combined with the new Redirect Rule sending `/*`
straight back to `esolia.co.jp/blog/*`, that is an **infinite redirect loop on
the blog's front door**. The forwarder dispatches first so it wins either way,
but the entries were removed rather than shadowed — a stale rule that is only
harmless by accident of ordering is a trap.

Also unlisted: seven places in that repo linked to the blog, three
`trackOutbound('blog.esolia.pro')` calls that became false once the links were
same-origin, and the build-time feed fetch.

**Lesson: grep the _other_ repo for the old hostname too.** An existing redirect
pointing at it is a loop waiting for the redirect rule.

### Things checked that needed nothing

Worth recording so they are not re-investigated:

- **`_site/_headers`**, `wrangler.jsonc`'s `run_worker_first`, and the blog
  Worker's own route matching all correctly stay unprefixed — the edge strips
  the prefix before dispatch. What the Worker _receives_ is unprefixed; what it
  _emits_ is not. That asymmetry is the whole point of `PUBLIC_BASE`.
- **Turnstile** — the widget enforces a hostname allowlist and already had
  `esolia.co.jp`. A missing hostname would have blocked every signup with the
  same silent signature as the `ALLOWED_ORIGINS` bug.
- **IndexNow** — a key hosted in a subdirectory authorizes URLs in that
  subdirectory.
- **`cms.blog.esolia.pro`** — the Redirect Rule uses `http.host eq`, an exact
  match, so the CMS subdomain was never at risk. Worth knowing before anyone
  changes that rule to a wildcard.
- **The VPS** — `blog-nightly-pull.sh` only pulls on a clean tree on main,
  fast-forward only, and restarts `lumecms` when config or deps change. It would
  have picked up the migration on its own. Nothing needed adjusting.

### A gate nobody had documented

esolia-2025 is a SvelteKit app, and **SvelteKit's CSRF protection rejects
cross-origin POSTs before `hooks.server.ts` runs** — so it now sits in front of
`/blog/api/*` as an outer gate, stricter than the blog Worker's own
`ALLOWED_ORIGINS`.

The two rejections are distinguishable, which is how to tell them apart when
debugging:

| Origin       | Response                                         | Meaning                                 |
| ------------ | ------------------------------------------------ | --------------------------------------- |
| ≠ app origin | `Cross-site POST form submissions are forbidden` | SvelteKit; the forwarder never ran      |
| = app origin | `Forbidden`                                      | reached the blog Worker's own allowlist |

Practical consequence: the blog's old-host allowlist entry does **not** protect
forwarded POSTs. It covers only requests that hit the blog Worker directly —
before the Redirect Rule went live, and during a rollback. An earlier comment
claiming otherwise was corrected.

## Part 2 — security and configuration

### CSP: added, and browser-tested

The blog had **no Content-Security-Policy**, at either hostname. It has one now,
in its own `src/_headers` rather than by applying esolia-2025's to the forwarded
response — so it holds whether the blog is reached through the forwarder or
directly, and it survives the service-binding hop.

`'unsafe-inline'` and `'unsafe-eval'` are not laziness: the blog is static HTML
from the assets layer, so there is no per-request step in which to mint a nonce,
and Alpine.js needs `eval`. Pagefind needs `'wasm-unsafe-eval'`.

**Testing earned its keep.** Fathom falls back to an **image** beacon, so
`img-src` needs `https://cdn.usefathom.com`. A deliberately tight
`img-src 'self' data:` silently broke analytics; only a
`securitypolicyviolation` listener caught it — a page-render check would not
have.

> **Trap for whoever tests this next:** `https://cdn.usefathom.com/` with no
> path 301s to `usefathom.com`, which the policy does not allow, so probing the
> bare URL reports a violation that says nothing about the real beacon. Use the
> full `?h=…&sid=…` form.

**Worker-rendered pages had no security headers at all** — not just no CSP.
`_headers` is applied by the static-assets layer and never reaches a Response
the Worker builds itself. The verify/unsubscribe pages now carry
`default-src 'none'` plus HSTS, `nosniff`, `X-Frame-Options` and
`Referrer-Policy`.

### Content-Signal

Applying the policy to blog content needed **no code** — robots.txt is read only
at the origin root, so once `/blog/*` is served from `esolia.co.jp`, that file
governs it.

What was added is the blog's own matching `robots.txt`, because "inert" only
holds while the blog is reached _through_ the forwarder. It is authoritative
whenever the blog answers directly: before the Redirect Rule went live, and
during a rollback. Previously it was a bare `Sitemap:` line — no Content-Signal,
no bot blocks — so blog content sat unprotected in exactly the moments things
were most in flux.

Both files now carry `use=reference` and disallow the newsletter API paths.
**They are a hand-sync across two repos and two formats**, so
`deno task check:robots` compares the `Content-Signal` line and the AI-bot
`User-agent` blocks against the live `esolia.co.jp/robots.txt`, and a weekly
workflow runs it. Schedule-only by design: a policy change takes two deploys and
the files legitimately differ in between, so a push trigger would cry wolf every
time.

### The security-verification flash: closed, not solved

Reported as a brief Cloudflare interstitial when moving between the blog and the
main site. **Two theories, both wrong**, and the firewall log disproved both.

From 500 events over ~44 minutes:

| Action            | Count |
| ----------------- | ----- |
| skip              | 467   |
| managed_challenge | 19    |
| block             | 14    |

All 19 challenges were working as intended and **none was us**: 16 from the
zone's own "certain countries" WAF rule (all CN, plus SG/US), 3 from Super Bot
Fight Mode's "manage definite bots". User agents were Sogou spider ×8,
Baiduspider, and Chrome UAs off Chinese ASNs.

The decisive checks: **events from Japan: 7**, none a challenge. **Challenges to
a real-browser UA from Japan: 0.** **Events on `/blog/*`: 210, every one
`skip`.**

Two corrections recorded honestly:

1. **JavaScript Detections was not the cause**, and turning it off — which had
   been suggested — would likely have made things _worse_. Cloudflare's docs are
   explicit that JSD _"runs on every HTML request without pausing or
   interrupting the visitor"_ and that _"enforcement against bots does not occur
   even if the cookie is flagged false"_. It only populates
   `cf.bot_management.js_detection.passed` for a WAF rule to act on; no such
   rule exists here. It is one of the signals that helps a real browser pass, so
   removing it means _more_ false challenges, not fewer.
2. **Super Bot Fight Mode was not the cause either.** The log shows it
   challenging only what it should.

Not reproducible afterwards. Most likely transient and tied to the cutover — a
full cache purge plus JSD's 15-minute `cf_clearance` lifespan, while crossing
rapidly between two Workers on one hostname.

**If it recurs, capture the Ray ID** from the interstitial. That maps to a
single firewall event and turns three theories into one answer. Nothing was
changed; `enable_js` stays on.

Incidental: the log shows **147 `/blog/*` requests from FR and 39 from US by
known-good bots in 44 minutes**. The blog is being crawled hard since the move.

## Part 3 — quality review

Sequence: audit-style passes first (objective, testable), subjective design work
after.

### Pass 1 — accessibility

Audited with **axe-core** (WCAG 2.0/2.1 A + AA + best-practice) in a real
browser, **both light and dark**, on listing and post pages.

|                 | Before | After      |
| --------------- | ------ | ---------- |
| Violation types | 5      | 1          |
| Critical        | 1      | 0          |
| Serious         | 2      | 1 (exempt) |
| Moderate        | 2      | 0          |
| Dark mode       | —      | clean      |

**Two were outright bugs, not tuning:**

Footer links carried `aria_label="…"` — **with an underscore**. Not an
attribute, so the browser ignored it. Worth knowing: _"fixing the spelling"
would have made it worse_ — a real `aria-label` overrides element text, so every
footer link would have been announced as "Site internal link" instead of
"Privacy Policy". The invalid attribute was removed along with a redundant
`sr-only` echo; links that genuinely open a new tab now say so, which is the
part that was missing.

The language switch was an `<a>` nested inside a `<button>` — two focusable
controls announced as a button that is really a link. Now a single `<a>` with
`hreflang`/`lang` so a screen reader switches voice.

Also: `role="menuitem"` with no menu parent (the critical failure), an empty
unlabeled `<nav>` landmark (because `topnav.links` is `[]`), and `h3` cards
directly under an `h1`.

**Contrast — seven fixes, all measured:**

| Element             | Was            | Change                      |
| ------------------- | -------------- | --------------------------- |
| Category chips      | 3.5–3.8:1      | text → `-900`               |
| Post metadata       | 2.51:1         | `zinc-400` → `zinc-600`     |
| "Hot" badge         | **1.66:1**     | white → `esoliaamber-950`   |
| Base link colour    | 4.39:1         | `zinc-500` → `zinc-600`     |
| Footer copy/address | 2.59:1         | → `zinc-600`                |
| Primary buttons     | 2.59:1         | `sky-500` → `sky-700`       |
| Language switch     | 2.26:1 blended | `sky-700/90` → `sky-800/95` |

Chip backgrounds and the amber badge keep their colour, so category
colour-coding still reads; only text darkens. Dark mode was audited separately
throughout — chips flip to a light background there, and a light-only audit
would have missed half the palette.

**One node remains** in light mode: the Subscribe button while _disabled_. WCAG
1.4.3 exempts inactive controls and the dimming is the affordance. Left
deliberately.

### Pass 2 — structured data

Four defects, three of which meant consumers got nothing usable:

| Defect                          | Impact                                                                     |
| ------------------------------- | -------------------------------------------------------------------------- |
| `@type: "blogPosting"`          | schema.org is case-sensitive — not a real type, so the block was discarded |
| `og:type: "blogPosting"`        | not in Open Graph's fixed vocabulary either                                |
| `url` / `image` missing `/blog` | advertised a URL that **301s** and an image that **404s**                  |
| no `publisher`                  | Google treats it as required for Article types                             |

**The URL bug had a misleading cause.** It looks like plugin ordering —
`json_ld` ran before `basePath`, while `metas` runs after and _its_ `og:url` and
`og:image` were correct. Moving `json_ld` later changed nothing. The plugin
resolves each URL as:

```js
new URL(dataValue, site.url(data.url, true));
```

The base is right. The value from `=url` and `=image` is **root-relative**, and
a root-relative path resolves against the origin, discarding the base path. The
value was wrong before ordering came into it.

A process step now re-applies the prefix, scoped to keys naming a first-party
resource (`url`, `image`, `@id`, `logo`, `contentUrl`, `thumbnailUrl`) and
explicitly **excluding `sameAs`**, which holds external profile URLs that
prefixing would corrupt. It no-ops when the base path is `/`, so preview is
unaffected.

Verified: 66 posts, 0 remaining origin-rooted URLs; a sampled `url` and `image`
now both return 200.

### Pass 3 — AI discoverability

`llms.txt` and `llms-full.txt` had **no mention of the blog**. `robots.txt`
points at the blog sitemap, which covers crawlers — but `llms.txt` is read by
things that do not crawl, and they take it at its word. Its word was that ~90
bilingual posts did not exist.

Added a `## Blog` section with both language indexes, the sitemap, both feeds,
and a sample of real posts (8 per language in `llms.txt`, 15 with summaries in
`llms-full.txt`), read from the same cached feed the homepage cards use so it
tracks new posts automatically.

Also disambiguated a naming collision: the existing entries described
`/articles/` as an _"IT tips and insights blog"_. That was loose before and
actively misleading once a separate thing called **the blog** appeared on the
same origin. `/articles/` is **The eSolian**, a named publication with its own
masthead — articles, insights and case studies. Both are now named properly.

### Pass 4 — dead source

The entire custom CSS layer was unreachable. Nine partials were imported only by
`src/styles.oldcss`, which is not a `.css` file, so `site.add([".css"])` never
matched it and Lume never processed it. None of it had ever been in effect — the
English hyphenation setup, the Japanese `hyphens` rule, `text-wrap` on headings,
the article heading scale, the letter-spacing variables. Twelve unreferenced
templates and layouts alongside it, mostly earlier drafts superseded by a
sibling.

Twenty-one files moved to `archive/`, outside `src/`. Two lessons recorded in
`archive/README.md`:

- **A filename search is the wrong instrument for Lume components.** Templates,
  layouts and stylesheets all reference by path, so searching for the filename
  is correct for them. Components are used as `comp.icon({ … })`, which never
  contains the filename. `_components/icon.vto` was archived by mistake on that
  basis; the build failed loudly and it was restored.
- **A naive hash of the built HTML cannot verify "nothing changed".** `_data.ts`
  stamps a fresh `cacheBuster` into every build, so two builds of byte-identical
  source hash differently. Strip `?cb=<digits>` first. With that, 2754 files and
  hash `60a55b08` before and after.

Also worth knowing: `src/generators/*.page.js` look unreferenced to any grep
because Lume auto-discovers `*.page.js` by convention rather than importing it.
They are live.

### Pass 5 — typography

The blog had no typography CSS in effect (see pass 4). A live layer now exists
at `src/_includes/css/type.css`, recovering the English hyphenation work from
the archived file and adding Japanese handling it never had:
`line-break:
strict` for kinsoku shori, `overflow-wrap: break-word` for long
Latin runs, `text-spacing-trim: auto` for CJK punctuation, and `palt` on
`h1`–`h3` where loose full-width kana spacing actually shows.

**Two orphan bugs, both caught by looking at the rendered page rather than the
code.** A single 「は」 stranded on its own line in the ja hero — not a wrap
artifact but a hardcoded `<br class="hidden md:inline">` that assumed the text
would wrap at a particular point. And the external-link arrow could wrap away
from its link: hibana's `externalLinksIcon` emits `after:content-['_↗']`, where
`_` is Tailwind's stand-in for a space, so a break can land between text and
arrow. Japanese makes it far likelier, since there is a break opportunity
between almost every pair of characters. Fixed with `U+00A0`.

That override had to be **unlayered**: Tailwind's `utilities` layer outranks
`base`, so `@layer base` loses to the very class it overrides. Unlayered rules
beat every layer.

**The responsive sweep found no overflow at all** — 8 widths × 2 languages, zero
at every one, later re-confirmed at 320–1920 across ja, en and a post page. What
it did find was a scale that stepped and then stopped:

|         | Before                                   | After               |
| ------- | ---------------------------------------- | ------------------- |
| Hero h1 | 36px, snap to 48px at `sm`, flat to 1536 | 36 → 56, continuous |
| Post h1 | five breakpoints (`xl`→`5xl`)            | 20 → 48, continuous |
| Card h2 | flat 18px, phone to 27-inch              | 18 → 22             |

Nine breakpoint declarations became three `clamp()` tokens in `@theme`, anchored
to the sizes already in use. That is why tuning felt fiddly: with steps, every
intermediate width is served by whichever step it lands in, so the fix always
looks like adding another breakpoint.

**Measurement note.** The first attempt at the sweep was invalid: constraining
`document.documentElement.style.width` does not move the viewport, so media
queries never fire and `fixed` elements still measure against the real window.
It reported 1408px of overflow that did not exist. Same-origin iframes sized to
each width do work — media queries resolve against the iframe. But the site's
own `X-Frame-Options: DENY` and `frame-ancestors 'none'` block that, so the
build has to be served without those headers for the measurement.

### Pass 6 — `comp.icon` rendered as literal text (found in production)

Reported by Rick from a live page, not by any check here — worth noting, because
none of the passes above would have caught it. The broken output was valid HTML
containing visible text; nothing 404s, nothing errors, and the accessibility and
structured-data passes had no reason to look at paragraph prose.

`src/_components/icon.vto` — the component that lets staff drop a Phosphor icon
into post markdown — emitted its `<img>` tag across four lines. Post markdown
runs with `breaks: true` and `typographer: true`. So:

1. `breaks: true` turned the newlines _inside_ the tag into `<br>`, splitting
   the tag apart;
2. markdown-it therefore stopped recognizing it as inline HTML and rendered the
   attributes as visible text;
3. `typographer: true` curled the quotes on the way out;
4. the orphaned `>` at the end started a `<blockquote>`, swallowing the rest of
   the sentence.

Readers saw `<img class="size-4 ..." src="..." inline` mid-paragraph. **67
occurrences across 10 posts** (five ja/en pairs).

The fix is to keep the tag on one line. The part worth remembering is the second
half: **`deno fmt` wraps it straight back to four lines**, and CI runs
`deno lint && deno fmt --check && deno task lume`, so the next formatting run
would have silently restored the bug with nothing failing anywhere. A one-line
fix here is not stable unless the formatter is told to leave it alone —
`src/_components` is now excluded from `fmt`, with the reason written into the
component itself so it travels with the code.

This is the same shape as the migration bugs in Part 1: **a silent failure in a
build that reports success.** The difference is only where it surfaced. Issue
#324, PR #325.

### Remaining

Accessibility, structured data, AI discoverability, dead source, typography and
JS organization are done — the last of those landed with the search dialog's
focus management in PR #323. Still open: **CSS review** and **hero area design**
(a subtle tech motif at the upper right).

Worth judging on screen rather than in a diff, now that the typography layer is
deployed: `text-spacing-trim` and `palt` on a real Japanese post, and the
640–1024 band where the hero h1 is now 41–48px rather than a flat 48. The latter
is taste, not measurement — raising the `clamp()` intercept from `1.75rem`
restores the old size.

Carried into those passes:

- **3 pre-existing TypeScript errors** in `src/_data.ts` (`Intl.DateTimeFormat`
  spread arguments). Not introduced here, and `deno check` is not in this repo's
  CI, so they are invisible today.
- The `role="menubar"`/`menuitem` pattern still present on the (currently empty)
  top nav. Valid ARIA if it renders, but menu roles imply keyboard behaviour
  that is not implemented; plain navigation links would be better.
